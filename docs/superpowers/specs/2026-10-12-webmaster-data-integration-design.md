## 1. 需求原文与拆解

产品负责人原话（2026-10-11）：

> 在 demo 页面中存在网站优化建议，这部分优化建议目前是怎么得出来的，是否能接入像
> google search console 和 google trends baidu 站长第三方可靠的数据信息等，可以统计网站关键词
> 曝光和点击等关键数据，然后将这些有说服力的数据进行统计显示出来，然后提供用户查看，
> 并可以自动分析网站的优化细节。

拆成五问：

1. **今天的"网站优化建议"是怎么得出来的？** ⇒ §2 交底：三处上屏的"建议"，**没有一处是算出来的**，
   全是 `demo/seed/` 里的手工静态值。这是 AGENTS 规则 9 的直接后果（领域算法是 Rust 纯函数，
   demo 只端预置值），不是缺陷；但真后端侧**同样没有实现**（`generate_handler![]` 里只有 40 条命令，
   `action_*` / `diagnosis_*` / `site_*` 一条都没有），所以这不是"改造现有算法"，而是"从零建一条数据链"。
2. **能不能接 Google Search Console / Google Trends / 百度站长？** ⇒ §3 调研：**能，但可得性差两个量级**。
   GSC 有正式 API（传统搜索数据）；Google Trends **没有公开 API**（官方仍是 alpha 白名单）；
   百度侧最有价值的《AI 流量分析》**只有后台、没有 API、连字段文档都还没公开**；
   🔴 而且**三家 AI 引用报告（百度 / GSC / Bing）一律 UI-only**⇒ 文件导入与人工填报**不是退路，是主路**。
3. **曝光与点击能不能统计显示、能不能汇总？** ⇒ 能，且**应当汇总**（DR-95 修订）：
   跨平台求和是合法的（Google 上的一次曝光与百度上的一次曝光是**不相交的事件集合**），
   但必须**分层归一**——A 类可加、B 类只能重算不能平均、C 类平台独有单独展示。
4. **"有说服力"从哪来？** ⇒ 不是从更多数字来，是从**出处 + 诚实的口径**来：客户自己后台的数字
   （"你自己账号里看到的"）比我们的抽样估计有说服力得多；而一个会因为平台采样或数据延迟
   莫名掉 40% 的合计数字，被追问一次就全线崩塌 ⇒ DR-109 / DR-110 那两道护栏是"说服力"的一部分，不是可选项。
5. **"自动分析网站的优化细节"能做到哪一步？** ⇒ 6 条**可判定**规则（DR-100），每条都有明确输入、
   阈值、输出处方类别，并且**回指既有模块**（关键词库 / 行动中心 / 站点接入 / 文章管理）。
   🔴 规则是 `geo-domain` 纯函数，**demo 只端静态机会清单**（规则 9）——界面上常驻说明。

🔴 但"导入优先"**不等于**"OAuth 可选"：三家 OAuth 全在路线图上（DR-93），导入解决**覆盖面**、
OAuth 解决**新鲜度**，两者互补。**只做 OAuth 的话，AI 引用数据一条都进不来。**

## 2. 现状交底：今天那三处"优化建议"分别是怎么来的

| 上屏的面 | 数据从哪来 | 是算出来的吗 | 真值源（本轮一行未动，给行号） |
|---|---|---|---|
| 行动中心「Top 处方」10 条 | `SEED_ACTIONS` 手工写死 | ❌ 不排序、不新增；`action_update_status` 只翻状态 | `apps/desktop/ui/src/demo/seed/actions.ts:22`、判据在 `apps/desktop/ui/src/demo/handlers/action.ts:46` |

| 站点接入的页面清单与 `crawlable` | `SEED_SITE_PAGES` 静态 | ❌ **不是爬出来的**，界面有常驻说明 `site.staticNote` | `apps/desktop/ui/src/demo/seed/site.ts:52` |
| 站点通道自检结论 | `SEED_SITE_CHANNEL_PROBES` 静态 | ❌ **不联网**（规则 2） | `apps/desktop/ui/src/demo/seed/site.ts:126` |

🔴 **结论一句话**：demo 里的"建议"是**产品口径的样例**，价值在于让产品负责人看清"一条处站长什么样"
（影响范围 / 预期收益 + 依据 / 实施难度 / 负责人建议 / 可交付物 / 是否 1 小时内能做完），
**不在于它对这个站点成立**。处方 `rationale` 里引用的数字（覆盖率 42%、自有页占 31%、被引域名 47 个、
决策层提及率 28%）与 `seed/diagnosis.ts` 逐条对齐、横看竖看不矛盾——这是**自洽**，不是**真实**。

**这一轮要补的正是这个缺口**：处方今天的依据是"我们抽样问了 62 道题得到的模型回答"，
缺的是"搜索引擎官方口径下这个站点真实的曝光 / 点击 / AI 引用"。前者是我们的**估计**，
后者是客户账号里的**事实**。把后者接进来，处方才从"看起来有道理"变成"有出处"。

**已经能复用的既有能力**（本轮设计刻意贴着它们长，不另造一套）：

- `crates/geo-crawler/`：同域爬取、`robots.txt` 解析、页面角色分类（home/about/product/faq/contact/other）、
  正文抽取 ⇒ 规则 4/5（DR-100）要拿它与第三方数据交叉，**这是自有探测与站外数据唯一的咬合点**。
- CSV 导入姿态：`prompt_set_import_csv` 的表头校验 + 行级错误 + 错误行号口径
  （`apps/desktop/ui/src/api/constants.ts:7`、`demo/handlers/prompt-csv.ts`）⇒ DR-98 照抄。
- 连接面姿态：`site_channel_upsert` / `site_channel_remove` / `site_channel_test` 三件套 +
  `credentials_state` + `checked_at` / `check_detail`（`apps/desktop/ui/src/api/types-site.ts:227`）⇒ DR-97 照抄。
- 一次往返拿全首屏：`action_board` / `collection_board` / `site_board` / `kb_board` ⇒ `search_board` 同款。
- 钥匙串：`SecretStore` trait + `secret_ref(kind, provider)`（`crates/geo-store/src/secret.rs:30`）⇒ DR-96。

## 3. 全球市场调研：数据源可得性矩阵

### 3.1 传统搜索的官方数据（曝光 / 点击 / 位次）

**Google Search Console — Search Analytics API**（`googleapis.com/webmasters/v3/sites/{siteUrl}/searchAnalytics/query`）
是这一族里**唯一成熟可编程**的：

- 维度 `query` / `page` / `country` / `device` / `date`，指标 `clicks` / `impressions` / `ctr` / `position`；
  `type`（searchType）枚举 = `web` / `image` / `video` / `news` / `discover` / `googleNews`
  ⇒ 🔴 **没有生成式 AI 这一档**，AI Overviews 的点击与曝光是**混在 `web` 里**的（可经 API 拿到，但分不出来）。
- 配额：单次 `rowLimit` 1–25,000（默认 1,000，用 `startRow` 翻页）；**每种 searchType 每天最多 5 万行/资源**
  （官方"使用限制"页原文口径），超出即**采样**，不是报错；另有 QPS 短期配额与 1 天长期配额，
  官方建议的姿态是"**每天查一天**"而不是查长区间（按 page+query 分组的查询最贵）。
- 数据延迟约 2–3 天，保留约 16 个月；2025-04 起 Search Analytics API 支持**小时级**数据。
- 鉴权：OAuth scope `https://www.googleapis.com/auth/webmasters.readonly`（或 `webmasters`）。
  🔴 这是 **sensitive scope**（不是 restricted）⇒ 需要走 Google 应用验证才能去掉"未验证应用"警告，
  但**不需要 CASA 安全评估**。桌面端按 `installed` 应用类型注册 + loopback 回环重定向。
- 另有 **BigQuery 批量导出**（免配额、免采样），是重度用法的正路；先例：Peec 用 BigQuery MCP 取 GSC。
- 🔴 **中国可达性**：`googleapis.com` 在中国大陆不可达。桌面端的请求从**用户本机**发出
  ⇒ 客户自己有出海网络就能用，我们不需要（也**不应该**）内置代理。这条决定了 GSC 只对
  **跨境 / 出海**客户线成立，对纯内销客户是 0 价值。

**Bing Webmaster Tools API**（`learn.microsoft.com/en-us/bingwebmaster/`）：

- 官方 API 首页明列 **Rank & Traffic Stats / Link Details / Keyword Details / Crawl Stats / URL Submission**；
  OAuth 2.0（Azure AD 应用注册）。
- 🔴 首页挂着一条 Note：**"Legacy SOAP and POX APIs will be retired on August 31, 2026.
  Migrate to our REST APIs."**（本轮 2026-10-11 亲自核到）⇒ 网上大量教程里的
  `ssl.bing.com/webmaster/api.svc/json/GetPageQueryStats?...&apikey=` **已过时**，不能照抄。
- 数据保留 16 个月。**Bing 在国内也不可达**（`cn.bing.com` 可达但站长工具与 API 走全球域）。

**百度搜索资源平台**（`ziyuan.baidu.com`）：

- 传统工具（**索引量 / 流量与关键词 / 抓取频次 / 抓取诊断**）⇒ 🔴 **全部只有后台，没有公开数据 API**。
- 唯一开放的接口是**收录推送**（普通收录 / 快速收录的 URL 主动推送，日配额量级 10 万），
  那是"**写**"（提交 URL），不是"**读**"（拿曝光点击）⇒ 对本轮需求无用（M6.5 的 spec §2.4 已把它归到索引推送那条路径）。
- 站点验证是前提（文件验证 / HTML 标签 / CNAME），这一步**只能客户自己做**，我们无法代做。

**头条搜索站长平台**（`zhanzhang.toutiao.com`，亦 `om.toutiao.com`）：

- 后台有「**流量与展示量**」：官方定义 **展现量** = "搜索用户通过检索关键词，头条搜索结果中展现网站的次数"，
  **点击量** = "搜索用户在头条搜索结果中点击到网站的次数"；给**近一个月每天**的数据、每天更新，
  新注册站点有延时。另有索引量、抓取频次调整。覆盖抖音 / 头条搜索。
- 🔴 同样**只有后台，没有公开数据 API**；开放的只有 sitemap / URL 提交 / 死链提交 / 自动收录 JS。

### 3.2 AI 搜索的官方数据（GEO 产品的命门，2026 年刚刚出现）

这一族是本轮调研里**最值得接、也最难接**的一块——它直接回答"我的内容有没有被 AI 引用"。

**百度搜索资源平台《AI 流量分析》**（2026-09-11 上线，2026-09-16 起向站长推送站内通知）：

- 五项核心指标（官方通知口径）：**AI 引用量**（站点页面被 AI 答案引用的次数）、
  **AI 曝光量**（用户看到引用页面链接的次数）、**AI 点击量**（用户点击引用页面的次数）、
  **AI 点击率**（点击量 ÷ 引用量）、**引用页面量**（有多少个页面曾在 AI 体系中被引用过）。
- 两张细分表（官方通知口径）：**AI 引用热门关键词**（哪些搜索词触发了内容被引用，附各项数据）、
  **AI 引用热门页面**（最常被引用的页面）。
  🔴 **2026-10-12 实测两轮修正**：页面为**三段**——AI 引用概览 / AI 引用趋势 / AI 引用热门关键词；
  第一轮只看到关键词表带「下载表格」，第二轮确认**「热门页面」表同样存在且带下载**
  （空站点时该表不在首屏渲染、但下载入口在，产品负责人已取到文件）；概览与趋势**仍无导出**。
  ⇒ **页面级（`page_url` 维度）数据有官方导出**，表头原文
  `页面 | AI引用量 | AI曝光量 | AI点击量 | AI点击率`，
  已录 `fixtures/search/baidu_aiflow_hot_pages_empty_2026-10-12.xlsx`；两张表**都没有日期列**。
- **入口与官方公告（2026-10-12 核实，一级出处）**：后台导航已把《AI 流量分析》挂成**独立分组**，
  路由 `https://ziyuan.baidu.com/aiflow/index`（公开首页与公告页头部导航可见，**无需登录即可确认路由存在**）；
  官方公告《【功能上线】AI流量分析功能上线公告》全文在
  `https://ziyuan.baidu.com/college/videoinfo?id=3519`，原文只承诺"提供站点内容在传统搜索场景下
  AI 引用、曝光、点击等数据"并声明"正在分阶段开放，数据服务尚未正式启用"，
  🔴 **全文零次出现"导出 / 下载 / 复制 / CSV / Excel / API"**——但**公开材料沉默 ≠ 没有**：

**Google Search Console《生成式 AI 效果报告》**（2026-06 宣布，Search 与 Discover 各一份）：

### 3.3 站内分析（有点击、有搜索词，但没有曝光）

**百度统计 API**（`tongji.baidu.com`）：

- OAuth 2.0，提供**搜索词 / 来源分析 / 落地页 / 访问明细**等报表；
  🔴 配额官方口径：**每账号每周 50,000 次，每周六统一清零**（百度统计帮助中心"问题汇总"原文）。
- 它给的是"**用户搜什么词进到了站内**"（= 点击侧），**不给曝光**⇒ 单独用它算不出 CTR，
  必须与百度搜索资源平台的关键词数据配对（而后者没有 API）⇒ 这是国内路径**结构性的一道缝**。
- 是国内客户**命中率最高、审批最轻**的一个 API（客户多半已经装了百度统计代码）。

**GA4 / Google Analytics Data API**：同族，国内可达性问题与 GSC 相同 ⇒ 与 GSC 打包成"出海客户线"。

### 3.4 关键词量与趋势（用户点名的 Google Trends 在这里）

- 🔴 **Google Trends 没有公开 API**。官方 **Trends API 仍是 alpha**（2025-07 在 Search Central
  "What's new" 里以 "Introducing the Google Trends API (alpha)" 出现，需申请白名单，本轮调研时**仍未 GA**）。
  非官方 `pytrends` 走内部接口，**限流严重、随时失效、且违反 ToS** ⇒ 桌面端商业产品**不能用**。
- 替代：**DataForSEO Trends API**、**SerpApi Google Trends**（均为付费聚合，按量计费）。
- 国内关键词量：**5118 API**（36 个接口，¥0.003–0.015/次量级：关键词挖掘、百度排名、收录查询、长尾词）；
  **DataForSEO**（Labs API ~$0.00012/item 起、Baidu Organic SERP ~$0.0006/SERP、Keyword Data API 给搜索量）；
  **SerpApi** 支持 baidu 引擎端点。
- **不推荐**：Google Ads Keyword Planner API（需 developer token + 审批，重）、
  百度营销 API（需代理商资质，重）⇒ 两者都是"为了一个搜索量数字过一道商务审批"，MVP 不值。

### 3.4b 搜狗站长平台 / 360 站长平台（二期补研，2026-10-12）

产品负责人点名"后期可能还需要对接搜狗或 360"⇒ 本轮先把可得性钉死，实现放二期（DR-92 `phase: 2`）。

**搜狗站长平台**（`zhanzhang.sogou.com`，现称"搜狗搜索资源平台"）：

- 「流量与关键词」官方说明逐字口径：**"站长可通过此工具查询站点在搜狗的流量来源关键词信息，
  可以获得的信息包括近一月内站点在搜狗展现的所有关键词，关键词对应的展现量和点击量，
  点击关键词可查看该关键词下获得点击的详细 URL。"** ⇒ **这是国内四家里字段最全的一个**
  （关键词 × 展现量 × 点击量 × 落地 URL，与 GSC 的 `query × page × impressions × clicks` 几乎同构）。
- 官方注意事项三条：① **支持子域名级别查询，不支持目录级别**；② 关键词信息每天更新，
  **每日 15:00 之后可查询前一日数据**；③ 🔴 **"点击率为点击量与查询量的比值"**——
  **又一个分母口径**（百度 AI 是 ÷ 引用量、GSC 是 ÷ impressions），坐实 DR-95 的 B 类必须自己重算。
- 🔴 **没有读数 API**：开放的只有 sitemap 提交（**且 sitemap 是邀请制**）、中文站点名、压力反馈。
- **战略价值被低估**：搜狗已被腾讯整合，是**微信搜一搜的底层搜索引擎**，腾讯搜一搜（含搜狗）
  份额约 10%。对"目标客户是微信重度用户"的 B2B 中小企业，这是百度覆盖不到的场景。
  ⇒ 二期里搜狗应当**排在 360 之前**。

**360 站长平台**（`zhanzhang.so.com`）：

- 数据分析覆盖**收录情况、索引状态、抓取压力与流量数据**；另有移动适配、官网认证、蜘蛛 IP 公告。
- 🔴 **没有读数 API**：开放的是推送侧（`https://data.so.com/indexsubmit`，站内获取 token，
  `Content-Type: text/plain` 逐行提交 URL）⇒ 与百度收录推送同族，是"写"不是"读"。
- 份额不低（PC 端渠道强，各来源口径 12%–17%），但**关键词级数据的公开口径不如搜狗清楚** ⇒ 二期排搜狗之后。

🔴 **一条反面提醒（影响 DR-111）**：市场份额数据**各来源差异极大**——同一时期，
一家口径是百度 38.1% / 字节系 25% / 360 17.25% / 腾讯搜一搜（含搜狗）10%，
Statcounter 口径是百度 53.32%（移动 65.56%）/ 360 17.25% / Bing 16.93%。
⇒ 两件事：① 这恰好论证了"**不要我们自己估流量、只用客户后台的真数**"（§3.6 对 Ahrefs/Semrush 的否定）；
② **产品里不得硬编码"默认该接哪几个源"**，只能按客户自己的流量来源推荐（DR-111）。

### 3.4c 自动化获取的边界：API / 模拟登录 / 本机只读屏（2026-10-12 补研，含出处）

产品负责人问：阻塞项（百度《AI 流量分析》无 API、导出能力未证实）**能不能靠 API 接口、
或"用户提前配置好账号密码 + 模拟登录抓网页"解决**？⇒ 三条路径逐一核，**每条都给出处**。

#### 路径 A：官方 API —— 不存在，不是我们不做
- 百度搜索资源平台**只开放收录推送**（普通收录 / 快速收录的 URL 主动提交），
  索引量 / 流量与关键词 / 抓取频次 / 《AI 流量分析》**一律只有后台**（§3.1 已核）。
- 平台官方定位（`ziyuan.baidu.com` 首页自述）："百度搜索面向合作伙伴的官方平台，为开发者、内容创作者、
  站点管理者等伙伴，提供优化工具、数据、课程、Q&A 等服务"——**"数据"是给站长在后台看的，不是给第三方调的**。
- 🔴 **不要把两件事混为一谈**：百度确实在大规模开放 API，但开放的是**搜索能力**而不是**站长数据**——
  2025-04-25 Create 大会推出"百度搜索开放平台·AI 开放计划"，支持 **MCP 标准**、建 MCP server 发现平台
  （出处：`baike.quark.cn/baike?id=bc4bf83a1a3c838746179a8635f90588`）；
  2025-11-13 百度世界大会宣布"百度搜索 AI API 全面开放，已有 **625 家厂商**通过百度智能云接入百度搜索 API"
  （出处：`i.ifeng.com/c/8oFBjqRyxPC`、`new.qq.com/rain/a/20251114A00KX300`）。
  那是**给智能体检索全网内容**用的，与"把某个站点自己的曝光/引用数据交给第三方工具"是**两个方向**。
- **但方向上值得期待**：《AI 流量分析》2026-09-11 才灰度、**连字段文档都没公开**（§3.2），
  一个刚出生的报表通常先有后台、再有导出、最后才有 API。⇒ DR-108 的目录表可插拔就是为这一天准备的。

#### 路径 B：模拟登录 + 抓私有接口（用户预配账号密码）—— 🔴 **裁定不做**，四条理由都有出处

**B-1 平台协议直接禁止出借账号密码。**
《百度用户协议》账号安全条款原文：**"用户不得将账号、密码转让或出借给他人使用"**；
账号管理条款原文：**"百度账号所有权归百度公司所有，用户仅享有使用权"**，
且"用户应妥善保管，并**对以其账号进行的所有活动承担法律责任**"
（出处：`baike.quark.cn/baike?id=661efeec9e284a429df0c39160546246`）。
⇒ 让客户把百度账号密码填进我们的产品，**是让客户违约**；而且账号所有权归百度，
**客户自己的同意也不足以授权我们**——这正好落在下面 B-2 的第二重授权上。

**B-2 "三重授权原则"：用户授权 + 平台授权 + 用户授权，缺一不可。**
- 确立于 **新浪微博诉脉脉案**（北京知识产权法院二审终审，**(2016)京73民终 588 号**，
  2016-12-30 宣判，国内首起大数据不正当竞争纠纷案）：脉脉未经用户同意、也未经开放平台授权，
  获取并使用平台用户信息，构成不正当竞争，**判赔经济损失 200 万元及合理费用 208,998 元**
  （出处：`victory.itslaw.cn/victory/api/v1/articles/article/805e6593-dc90-48dc-a857-5745e8605af8`、
  `baike.baidu.com/item/三重授权原则/66725840`、`www.deo.org.cn/article/gfzy_hjbz/detail1084.html`）。
- 在"**头腾大战**"（微博诉今日头条）中被再次确认，法院认为该原则"**已经成为开放平台领域网络经营者
  应当遵守的商业道德**"，并细化：第三方获得平台授权后，数据获取与使用须遵循"**合理、正当、必要**"，
  **仅能将数据用于登录目的**，不得转授权（同上 无讼 出处）。
- 学理上的留白也要认：刘晓春（中国社会科学院大学法学院）指出，该案**没有明确回答**
  "经用户同意但未经平台同意的抓取是否必然不具正当性"（出处：`law.ucass.edu.cn/info/1985/6825.htm`）
  ⇒ 即"用户授权了就一定安全"这个抗辩**在学理上未定、在判例主流上不利**。
- 我们的情形：**用户授权有、平台授权无**（百度搜索资源平台从未向我们开放）⇒ 第二重缺失。

**B-3 2025 年修法后有了明确条文，且已有判例。**
- 《反不正当竞争法》（2025-06-27 第十四届全国人大常委会第十六次会议**第二次修订**）
  **第十三条第三款**（俗称"数据专款"）原文：
  **"经营者不得以欺诈、胁迫、避开或者破坏技术管理措施等不正当方式，获取、使用其他经营者合法持有的数据，
  损害其他经营者的合法权益，扰乱市场竞争秩序。"**
  （出处：国家市场监督管理总局法律全文
  `www.samr.gov.cn:85/zw/zfxxgk/fdzdgknr/fgs/art/2023/art_3737890d856a4e44a8ea07c50c90c116.html`；
  条文解读见广州知识产权法院 `www.gipc.gov.cn/front/showArticle?id=2941`）
- 四要件：客体（其他经营者**合法持有**的数据）/ 主体（经营者）/ 行为（**以不正当方式**获取、使用）/
  结果（损害合法权益、扰乱竞争秩序）。🔴 该条**不是一刀切禁止爬取**——
  "如果遵守了网站的爬取协议或平台规则，正常访问公开数据，一般不构成违法"
  （出处：`m.163.com/dy/article/L0EIAHDF05199NPP.html`）。
  **但站长后台的数据既不是公开数据、平台规则也不允许自动化访问**，正好落在禁止的一侧。
- **首例适用判决**：北京互联网法院 2026-06-05 宣判（**首例**适用反法"数据专款"），
  被告"通过获取网页源代码、编写爬虫程序的方式，**避开平台技术防护措施**，自动抓取全平台核心职场数据"
  并售卖访问权限，**判赔 23 万余元**（出处：`www.cnr.cn/mspd/msyx/20260605/t20260605_527649575.shtml`、
  `www.iprchn.com/cipnews/news_content.aspx?newsId=147446`）。
  🔴 判决书点名的平台防护措施是"**登录验证措施、访问权限管理措施、可追踪加密参数**"——
  百度搜索资源平台同样有登录验证与站点级权限管理；**绕过验证码 / 风控去自动登录，
  就是"避开技术管理措施"的教科书形态**。
- 同族先例：**酷米客诉车来了案**（(2017)粤03民初822号），突破技术防护措施获取非公开数据构成不正当竞争
  （出处：`baike.baidu.com/item/三重授权原则/66725840`）。

**B-4 就算不考虑法律，工程与商业上也扛不住。**
- **凭据性质错**：百度账号是**全身份凭据**（同一个账号通网盘 / 贴吧 / 知道 / 支付），
  不是受限、可撤销、最小授权的令牌 ⇒ 与 AGENTS **规则 3** 的精神（只存最小必要凭据、只进钥匙串）
  直接冲突。我们一旦持有，泄露的代价是客户的**整个百度身份**，不是"一个站长后台"。
- **风控会打到客户账号上**：百度登录有滑块 / 短信二次验证 / 设备指纹 / 异地登录风控。
  桌面端自动化登录**极可能触发风控**，后果是**客户的账号被限制或封禁**——
  🔴 这个后果我们无法在合同里转移，也无法修复，而客户丢失的是他官网在百度的**全部数据入口**。
  对一个卖 ¥15,800 的工具来说，这是**足以毁掉口碑的单点故障**。
- **私有接口无契约**：后台 XHR 端点随时改、常带 `sign` / 时间戳校验、灰度期字段还在变
  （§3.2 已注明平台**没有公开字段说明文档**）⇒ 维护成本无上限，且每次坏掉都是客户先发现。

#### 路径 C：用户本机 + 用户自己的浏览器会话（"只读屏、不碰凭据"）—— 🔜 **三期，且被产品定义挡着**
- 这是**唯一在架构上站得住**的自动化形态：不收集账号密码、由用户在自己的浏览器里登录、
  我们只读取**用户当前会话下、用户自己屏幕上已经渲染出来的数据**。
- **域外最新判例恰好支持这个架构，但支持得很窄**：
  **Amazon.com Services, LLC v. Perplexity AI, Inc.**, No. 26-1444（美国联邦第九巡回上诉法院，
  **2026-08-04**）撤销了地区法院的初步禁令并发回。法院认定：亚马逊很可能无法证明
  **Perplexity 本身**构成《计算机欺诈与滥用法》（CFAA）与加州《综合计算机数据访问与欺诈法》下的
  "**访问**"行为——因为 **Comet 浏览器运行在用户本地设备上、Perplexity 的服务器从未直接与亚马逊服务器通信**，
  真正"访问"平台的是**使用 AI 工具的用户本人**
  （出处：嘉润律师事务所双语分析 `www.dowway.com/news/2026-09-30/654.html`、
  `finance.sina.cn/2026-08-08/detail-inimqtzr4221907.d.html`、`news.qq.com/rain/a/20260811A0BE4X00`）。
  🔴 **但裁定范围明确受限**（同一出处逐字）：既未对实体争议作终局裁判，
  **也未为 AI 代理确立普适规则**、**更未赋予普遍抓取第三方平台数据的权利**，
  且**不排除依合同、隐私、反不正当竞争等其他法律承担责任**；连 user-agent 字符串的争议都没终局认定。
- 放到中国法下：我们的桌面端**同样是"请求从用户本机发出"**（DR-104 已经把这当成结构性优势），
  架构上与 Comet 同构 ⇒ Perplexity 案的**思路**可参考。但 🔴 **它挡不住 B-2 / B-3**：
  三重授权原则与反法第十三条第三款**不看请求从哪台机器发出**，看的是**有没有平台授权**、
  以及**有没有避开技术管理措施**。"用户自己登录"能解决"出借密码"这一条，
  解决不了"平台没授权我们自动化读取"这一条。
- 🔴 **而且这条路被上游需求真值源挡着**：`docs/GEO客户端-MVP产品定义-v1.md` §3.12（`:336`）
  **明确 ❌ 浏览器插件**，而"读用户当前浏览器会话"的标准实现形态就是浏览器扩展或内置浏览器。
  ⇒ **要走这条路，必须先改产品定义**，那是产品负责人的权限，不是本规格能裁的。
- 结论：**本轮与二期都不做**，登记为**三期选项**，并写清三个前置条件（DR-114）。

#### 路径 D（🆕 本轮采纳）：粘贴解析 —— 把"人工"这一步做到几乎零成本
- 客户在**自己的后台**把表格选中复制（Ctrl+A / Ctrl+C 或框选），粘进我们的文本框，
  我们解析 **TSV / HTML 表格 / 逗号分隔**三种常见剪贴板形态。
- 🔴 **为什么这条是合规的**：整个取数动作**发生在客户自己的浏览器里、由客户自己动手**，
  我们**不持有凭据、不向平台发请求、不绕过任何技术措施**——从三重授权的角度看，
  这里根本不存在"第三方获取平台数据"的行为，只有"用户把自己的数据交给用户自己装的软件"。
- 🔴 **为什么它比 CSV 模板好一个量级**：DR-98 原来要求"照我们的模板重粘一遍"（用户要重排列），
  粘贴解析**不要求列序**——按表头文字识别列（`alias_columns`，DR-108），用户零改造。
- 它同时是**导出能力缺失时的通用兜底**：百度《AI 流量分析》即使没有导出按钮，
  页面上那两张表也**能选中复制**⇒ 阻塞项被绕过，而不是被硬闯。

### 3.6 先行者怎么做（我们照抄与不照抄的）

- **Peec AI**：走 GSC → BigQuery → MCP，把搜索控制台数据喂给代理 ⇒ 印证"重度用法要绕开 API 采样，走批量导出"。
- **Profound**：为 Agents 提供 "GSC nodes" ⇒ 印证"搜索控制台数据是 GEO 产品的标准输入"。
- **Rankscale**：把 GA4 + GSC 与 AI 可见度关联（beta）⇒ 印证 DR-101 那条"站外真相 ↔ 模型抽样"的关联是行业共识方向。
- **Ahrefs / Semrush（2026-10-12 前瞻性侦查重写）**：它们的自动化**不是**登录客户控制台，而是**两条腿**——
  **腿 1 自建索引**：Ahrefs 官方自述 "crawl the entire web 24/7 and store petabytes"（ahrefs.com/big-data，
  一级出处），AhrefsBot 是 Cloudflare Radar 上 SEO 类第一活跃爬虫、SemrushBot 第二，Semrush 关键词库 210 亿+；
  2025 年 Semrush 的 **AI Visibility**、Ahrefs 的 AEO 追踪（ChatGPT / AI Overviews / Perplexity 引用）
  都建在**自家采样**上。**腿 2 官方 OAuth**：原生集成 GSC + GA4（用户授权与平台授权齐备）。
  🔴 **对照本产品的抄法**：腿 1 **抄其形不抄其量**——M3 采集（`geo-crawler`）就是我们自己的抽样腿，
  按关键词库向各家 AI 引擎提问并记录引用，**全自动、客户零动手**；但我们没有点击流、不建全网索引，
  所以自有抽样只回答"**AI 引用可见性**"，**不估算曝光 / 流量**——估算值在客户后台真实数字面前
  毫无说服力，而那恰恰是本轮需求的命门（原裁定维持）。腿 2 **全抄**（DR-93 三家 OAuth）。
  🔴 **它们不做的，我们也不做**：两家都**不登录客户站长后台**；百度《AI 流量分析》这类第一方控制台数据
  **全球没有任何厂商能自动拿到**（Semrush / Ahrefs 的百度覆盖被国内同行公认偏弱，更无百度控制台集成）
  ⇒ 产品负责人"参考 semrush / ahrefs 全自动化"的诉求，在这两家自己的实践里对应的正是
  "**自有抽样 + 官方 OAuth**"，**不是模拟登录**（§10.5）。
- **业界 GEO 服务商的实际做法（2026-08 行业选型稿，二级出处）**：给每个客户**人工注册并开通**
  Bing WMT AI Performance、以**报告截图**作为交付证据 ⇒ 连卖 GEO 服务的公司 today 也是半自动，
  印证"控制台第一方数据无自动通道"是**行业现状**，不是我们的能力缺口。
- **国内 GEO 发稿平台**（投媒网 / 优媒汇一类，2026 年的行业稿口径）：主打"API 深度数据对接 + 全链路数据追踪"，
  但追踪的是**发稿后的收录与分发**，不是客户站点的搜索表现 ⇒ 与本模块不重叠。

### 3.7 调研结论（七条，直接决定 §4）

1. **"接三个 API"这个提法不成立**：用户点名的三个源里，**只有 GSC 有能拿曝光点击的正式 API**；
   Google Trends 没有公开 API；百度侧最有价值的《AI 流量分析》连字段文档都没有。
2. **最有价值的数据全都没有 API**：三家 AI 引用报告（百度 AI 流量分析 / GSC 生成式 AI / Bing AI Performance）
   **一律 UI-only**；头条 / 搜狗 / 360 也只有推送 API、没有读数 API。
   ⇒ 想拿到 GEO 产品最想要的那份数据，**文件导入 + 人工填报不是退路，是主路**。
3. **国内与国际是两条独立的线，不能混设计**：可达性、验证方式、指标口径、客户命中率全都不同。
   国内客户 90% 用不上 GSC；出海客户 100% 用不上百度统计。⇒ DR-104 分组渲染。
4. 🔴 **口径差异是"分层"问题，不是"能不能汇总"问题**（2026-10-12 修订，原结论"任何统一都是造假"作废）：
   GSC `impressions`（结果中出现即计）、百度 AI 曝光量（"用户看到引用页面链接的次数"）、
   头条展现量（"搜索结果中展现网站的次数"）、搜狗展现量是**同一概念的四种计数规则**
   ⇒ **术语可以统一、A 类计数可以跨平台相加**（不相交事件集合）；
   但 **B 类比率绝不能平均**——百度 AI 点击率的分母是**引用量**、搜狗是**查询量**、GSC 是 impressions，
   三个不同分母的比率取平均得出的数字**没有任何解释**；
   **C 类平台独有维度**（Bing Grounding Queries、百度引用页面量、百度统计会话数）不得强行归一。
   ⇒ DR-95 的三层归一就是这条结论的落地。
5. **OAuth 的真实成本是审批而不是代码**：Google sensitive scope 要应用验证（周级）、Azure AD 要注册、
   百度统计 API 要后台申请。⇒ 落地顺序必须是"导入 / 填报先行"，但**三家 OAuth 全在路线图上**（DR-93），
   且 🔴 **GSC 的验证材料要现在就递**——它是唯一一个审批周期长到会卡住发布的。
6. **二期（搜狗 / 360）在架构上必须是"加数据"而不是"改代码"**：源会持续增加
   （产品负责人已点名这两家，神马 / 微信搜一搜独立入口也在可见范围内）
   ⇒ DR-108 的源目录表 + DR-107 的映射表是本轮**最重要的两条架构裁定**，
   它们决定的是"第 10 个源接进来要几天"，而不是"第 1 个源接进来要几天"。
7. 🔴 **"没有 API"不等于"只能模拟登录"**（2026-10-12 补研，§3.4c）：模拟登录抓后台这条路
   **法律与账号风险都不可承受**——百度用户协议禁止出借账号密码且账号所有权归百度（B-1）；
   三重授权原则缺"平台授权"这一重（B-2，新浪微博诉脉脉案，判赔 200 万 + 20.9 万）；
   反法（2025 修订）**第十三条第三款"数据专款"**已有首例判决（B-3，北京互联网法院 2026-06，判赔 23 万余元）；
   且自动化登录**极可能触发风控、封的是客户的账号**（B-4）。
   ⇒ 正解是 **`paste_parse`（粘贴解析，DR-113）**：取数动作发生在客户自己的浏览器里，
   我们不持有凭据、不发请求、不绕过任何技术措施——**阻塞项被绕过，而不是被硬闯**。


## 4. 裁定（DR-90 … DR-115）

### DR-90 · 总纲：三层数据流——自动采集为主喂料，导入 / 填报是**对账层**（2026-10-12 二次重定位）
🔴 **二次重定位（产品负责人第三轮指示"后期手动填报及导入基本不会使用，要全自动化"）**：
本模块的**主喂料永远是自动的**，分三层——
**L1 自有抽样（全自动）**：M3 采集（`geo-crawler`）按关键词库向各家 AI 引擎提问并记录引用，
这是我们的"AhrefsBot 腿"（§3.6），客户零动手；
**L2 官方 API（全自动，有 API 的源）**：百度统计 / GSC / Bing WMT 三家 OAuth（DR-93），令牌刷新后定时拉；
**L3 第一方控制台（半自动，对账层）**：无 API 的那批源（百度《AI 流量分析》、GSC 生成式 AI 报告、
Bing AI Performance、头条 / 搜狗 / 360），靠导出 / 粘贴 / 填报进来。
🔴 **L3 的定位是"对账"不是"喂料"**：用平台第一方数字**校准 L1 自有抽样的偏差**，
并在界面上把 L1 的覆盖率 / 最近运行时间做成常驻卡片——**客户看到的"自动化"由 L1 + L2 承担，
L1 + L2 拿不到的口径才落到 L3**。下面原文的"导入先行"因此只描述**落地顺序**
（demo 里唯一能真走通的形态），**不描述产品主数据流**。对账规则见 DR-116。

（以下为 2026-10-12 第一轮原文，描述落地顺序）
接入形态的**落地顺序**是 **① 文件导入（CSV）→ ② 人工填报 → ③ OAuth 直连**。理由三条（都由 §3.7 推出）：
最有价值的数据没有 API（结论 2）；OAuth 的成本是**审批**而不是代码（结论 5）；
demo 侧本来就不许联网（规则 2），导入是唯一能在 demo 里**真走通**的形态（规则 8 要求先在 demo 定稿）。
🔴 **"导入先行"不等于"OAuth 可选"**：百度统计 / GSC / Bing 三家 OAuth **全部在路线图上**（DR-93，

### DR-94 · 对象模型（`api/types-search.ts`）
照 `types-site.ts` / `types-article.ts` 的既有形状（值表 + 编译期完整性网）：

- `SearchSurface` = `web_search` | `ai_answer`（🔴 让同一张指标表能装传统搜索与 AI 搜索两种数据而不混淆，

- `SearchSource`：{ id, project_id, kind, **auth_mode**, **ingest_modes[]**（DR-93 / DR-113）,
  status, region, group（`webmaster` | `analytics`）,
  binding（`siteUrl` / `siteId` / 站点 URL，**非敏感**）, credentials_state, secret_ref,
  **data_through**, checked_at, check_detail, note, created_at, updated_at }。
  `status` **复用** `SiteChannelStatus` 四值（`not_configured` / `pending_verify` / `ready` / `failed`，
  `api/types-site.ts:83`）⇒ **不新造枚举**。
- `SearchQueryMetric`：{ id, project_id, source_kind, surface, query, page_url?, impressions?, clicks?,
  ctr?, citations?, avg_position?, **completeness**, period_start, period_end, **data_through**,
  imported_at, **native_extras?**, **mapping_version** }。
  - 🔴 指标全是 `number | null` 而**不是必填**：百度 AI 那份给引用量不给位次，GSC 给位次不给引用量，
    头条给展现与点击不给 query。**用必填字段逼用户填 0，就是把"没有这个指标"伪装成"这个指标是 0"**
    ——在 GEO 语境里这是致命的（"AI 引用量 0" 与 "平台没给这一列" 是完全不同的结论）。
  - `native_extras`：映射不上的**平台原生字段原样留档**（DR-107），界面上作为 C 类"平台独有维度"渲染。
  - `mapping_version`：这行是按**哪一版映射表**进来的（DR-107 的可审计性）。

  cited_page_count, period_start, period_end, data_through, imported_at }——百度《AI 流量分析》
  那五项的**项目级**快照。独立成对象而不并进 `SearchQueryMetric`：它是**汇总值**、没有 query 维度，

  这不是新采的数据，是把历次导入按周期堆起来的时间序列 ⇒ 这是 DR-106 拒掉 Google Trends 之后
  "趋势"这个需求的**唯一**满足方式（自己站点的趋势，不是全网趋势）。
- `SearchOpportunity`：{ id, project_id, rule_id, title, rationale, evidence_metric_ids[],

### DR-95 · 分层归一（🔴 2026-10-12 反转原裁定）

**我错在哪（原文照录，供后人别再犯）**：10-11 那版的 DR-95 是"**不做跨源归一、界面上没有总曝光这个指标**"。
它把两件不同的事混成了一件：

- "**术语**能不能统一"（展现量 / impressions / 曝光次数 = 同一个概念）⇒ **能**，这正是映射层该干的；
- "**数值**能不能直接加"⇒ 是另一个问题。

原裁定用后者的风险否决了前者，属于**过度保守**。而且**跨平台求和本身是合法的**：
Google 上的一次曝光与百度上的一次曝光是**两个不相交的事件集合**，相加不是重复计数
（这与"把同一平台的曝光和点击相加"那种范畴错误完全不同）。Semrush / Ahrefs / Sistrix 的
"总可见度"就是这么算的。产品负责人 2026-10-12 的指示是对的。

**修订后的裁定：分层归一，三层。**

| 层 | 指标 | 跨平台能否合并 | 规则 |
|---|---|---|---|
| **A 类·可加** | `impressions`（曝光 / 展现）、`clicks`（点击）、`citations`（AI 引用） | ✅ **可以求和** | 统一术语 + 统一单位；合计行**必须**带 DR-109 的区间与 DR-110 的完整性旗标 |
| **B 类·派生** | `ctr`（点击率）、`avg_position`（平均位次） | 🔴 **绝不对各平台的比率取平均** | 只能用 A 类求和后的**分子 ÷ 分母重算**；平台原生比率作为 C 类**同时保留** |
| **C 类·平台独有** | Bing `Grounding Queries`、百度 `引用页面量`、GSC 按设备位次、百度统计会话数 / 跳出率、搜狗"点击后可查详细 URL" | ❌ 不合并 | **单独展示 + 平台徽章**（产品负责人裁定 3 的原话），并在 tooltip 里给平台自己的口径说明 |

- 🔴 **B 类为什么必须重算**：三家的点击率分母**各不相同**——百度 AI 点击率 = 点击量 ÷ **引用量**；
  搜狗官方 = 点击量 ÷ **查询量**；GSC = clicks ÷ impressions。对三个不同分母的比率取平均，
  得出的数字**没有任何解释**。而"平台原生比率同时保留"是**信任问题**：
  客户在自己后台看到的数字必须能在我们这儿对上，否则他不信我们的合计。
- 🔴 **A 类也不是无脑相加**：只在**同一 `surface`** 内相加（`web_search` 与 `ai_answer` 分开合计）。
  跨 surface 相加要显式标注"传统搜索 + AI 搜索"，且默认**不做**——因为 AI 面的曝光
  （"用户看到引用页面链接的次数"）与传统面的曝光（"结果中出现即计"）**计数规则不同**，
  加起来的数只能作为量级参考。
- 撤回原文那条"**不提供总曝光这个指标**"。改为：**提供**，但合计行旁边**常驻**三样东西
  ——① 汇总区间（DR-109）、② 参与合计的源清单与各自 `data_through`、③ 完整性旗标（DR-110）。
  🔴 "有说服力"不等于"给个漂亮大数字"：一个能被追问到底的合计，才是有说服力的合计。
- 词典里为每个源准备 `webmasterData.sources.<kind>.metricNote`（口径说明），**常驻可展开**，不藏在问号里。

### DR-96 · 凭据面：账号级两段引用串，复用既有 `secret_*`
- 引用串形状 **`keyring://search/<source_kind>`**（例：`keyring://search/gsc`、`keyring://search/baidu_tongji`）。

- 🔴 真后端要落 OAuth 仍需改 Rust 两处（登记为 E-69）：① `apps/desktop/src-tauri/src/services/settings_service.rs:23`

⚠ 代价：明细量大时前端要扛（一个站点一个月按 query × page 展开可能上万行）⇒
真后端落地时要给 `search_board` 加分页或"只回 Top-N + 汇总"的形态，**这条登记进 E-67 的代价**。

### DR-98 · CSV 导入（🔴 2026-10-12 撤回一半）
- **撤回的部分**：原文那句"只认我们自己的模板、让用户把各平台导出**照模板重粘一遍**"**不再是唯一路径**。
  产品负责人裁定 3 要的是**映射层**，而映射层与"解析谁的格式"是两件事。
- **保留的部分**：仍然**不做"智能识别任意导出格式"**。给 GSC / 百度 / 头条 / 搜狗 / 360 各写一个
  导出格式适配器 = 五份漂移风险（平台改一次表头就崩），属于 §1 判据里"镜像成本 > 漂移风险"那一类。
- 🔴 **而且三家 OAuth 做完之后，这个问题大半自动消失**：API 返回结构化 JSON，根本不用解析 CSV。
  剩下需要 CSV 的只有**无 API 的源**（`baidu_ziyuan_ai` / `baidu_ziyuan` / `toutiao`，
  以及 GSC 生成式 AI 报告、Bing AI Performance 这两份 UI-only 的 AI 报告）。
- 🔴 **而对这批无 API 的源，`paste_parse` 优先于 CSV 模板**（DR-113）：客户在自己后台选中表格复制粘贴即可，
  **不要求列序**（按表头文字认列）⇒ "照模板重粘一遍"这个摩擦**取消**。
  CSV 模板降为**批量 / 归档**用途（一次导三个月历史数据时，文件比剪贴板合适）。
- 🔴 **2026-10-12 实测追加：`file_import` 必须吃 `.xlsx`，不只是 CSV**。百度《AI 流量分析》的官方导出
  **只有 xlsx**（§3.2 实测 ②），不接 xlsx 就等于导入按钮对真实客户是死的。解析分工：
  **demo 用 `fflate`（MIT，约 8KB）+ 一个约 150 行的最小 reader**（落 `api/search-xlsx.ts`，
  只认 `Sheet1` 的 `inlineStr` / `sharedStrings` / 数字 / 日期序列值；
  🔴 判据钉在真实空表 fixture 上）；**真后端用 `calamine` 重写同一契约**（两份解析器的漂移风险同 E-67 ③，
  登记 E-72）。保守备选（若评审嫌 demo 引依赖）：demo 对 `.xlsx` 返回稳定错误码并引导
  "用 Excel/WPS 打开后复制粘贴、或另存为 CSV"，xlsx 解析只落真后端。
  🔴 **默认走前者**：粘贴与导入共用同一套列识别，reader 只是"文本从哪来"的又一个答案，
  且官方唯一导出格式不接的话，导入按钮对真实客户就是死的。
- 🔴 **导出文件里没有日期列**（§3.2 实测 ③）⇒ 导入对话框必须让用户**确认该文件对应的区间**
  （默认手填页面当前所选区间 + 以导入时刻作 `data_through`）；汇总区间里这类源标
  `window_source: 'user_stated'`，文案写"区间由导入时确认"而不是"平台声明"（DR-109 / DR-110）。
- 🔴 **导出的 `AI点击率` 只作交叉校验、不作真值**：入库与展示一律按 `点击量 ÷ 引用量` **重算**
  （DR-95 B 类"只能重算不能平均"）；与文件值偏差 > 0.005 时给**行级 warning**（不阻断导入），
  因为灰度期平台自己的口径也可能在变。
- 因此导入模板按**指标形状**分三张（不按平台分），表头常量放 `api/constants.ts`
  （与 Rust 侧真值源同步的既有纪律）：
  - `SEARCH_WEB_CSV_HEADER`：`query,page,impressions,clicks,ctr,position`（GSC 导出与搜狗 / 头条 / 360 的
    关键词表都能对到这一张，**用户只需改列名**）；
  - `SEARCH_AI_CSV_HEADER`：`query,page,citations,impressions,clicks,ctr`（百度《AI 流量分析》两张表）；
  - `SEARCH_ANALYTICS_CSV_HEADER`：`query,sessions,landing_page`（百度统计；🔴 **没有 impressions 列**，
    因为站内分析给不出曝光——这一列的缺席本身就是 DR-95 那条"量纲不可混"的物证）。
- 🔴 平台原生列名到规范列名的对照**写进目录表**（DR-108 的 `alias_columns`），界面上给一张
  "各平台导出长什么样 → 对应我们哪一列"的对照说明；**不做自动嗅探**。
- 行级错误口径**逐字复用** `demo/handlers/prompt-csv.ts`（错误行号口径刚在 `08790a4` 那次提交里
  修正过镜像方向，不要再动）。

### DR-99 · demo 的能力边界（🔴 2026-10-12 放宽：映射与汇总 demo **真做**）
- **demo 真做**（这些是**确定性算术与查表**，不是领域算法，与 `prompt_set_import_csv` 真解析、
  `site-patch` 真生成落地包同一判例）：
  ① CSV 解析与行级校验；② **映射查表**（平台字段 → 规范指标，DR-107）；
  ③ **A 类跨平台求和**与 **B 类重算**（DR-95）；④ 按时间 / 平台 / surface 的**筛选**（DR-112）；
  ⑤ **交集区间**计算（DR-109）与 **陈旧 / 采样告警**判定（DR-110）；⑥ 接入建议的**展示**（DR-111）。
  🔴 这条放宽是产品负责人裁定 3 的直接收益：**demo 从此可以拿一份真的 GSC 导出 CSV 走查整条汇总链路**，
  而不是只看静态卡片——这是本轮 demo 价值的最大增量。
- **demo 不做**（规则 9 / 规则 2）：
  ① **DR-100 那 6 条规则的判定**（涉及阈值、经验区间、与爬虫结果交叉 ⇒ 是领域算法）；
  ② OAuth 全流程（连假授权都不演，只演 `status` 的四态）；③ 任何联网自检。
- 因此 `SEED_SEARCH_OPPORTUNITIES` 是**手工写死的 6 条**（每条规则一条），翻状态不重算、
  **导入 CSV 也不会长出新机会**；而 `SEED_SEARCH_QUERY_METRICS` 会被真导入的数据**替换/追加**，
  汇总数字**随之真变**。🔴 这个"一半真、一半假"的边界**必须在界面上说清**，
  否则产品负责人会以为"机会清单也该跟着导入变"。
- 🔴 三句常驻说明（照 M6.5 的 `site.demoBody` / `site.staticNote` 双常驻纪律）：
  ① `webmasterData.demoBody`——演示模式不联网、自检结论与机会清单都是预置的；
  ② `webmasterData.staticNote`——**机会清单不是算出来的**，导入数据不会改变它（但汇总数字会）；
  ③ `webmasterData.metricNote`——各平台口径不同，本页面按 A/B/C 三层归一，**比率不做跨平台平均**。
- 合规（规则 6）：机会文案与 CTR 基准**禁用绝对化用语**；基准只能表述为"同位次经验区间"，
  不得表述为"应该达到的点击率"。

### DR-100 · 自动分析的 6 条规则（`geo-domain` 纯函数，demo 只端静态）
落点 `crates/geo-domain/src/search_signal.rs`（不依赖任何其他 crate、不做 IO，规则 4）。
🔴 2026-10-12 起，规则的输入是**归一后的 A/B 类指标**（DR-95），不是单源原始值：

| # | `rule_id` | 输入 | 判据（阈值全部做成常量，不写死在逻辑里） | 输出机会 → 落点模块 |
|---|---|---|---|---|
| 1 | `high_impression_low_ctr` | 汇总 `impressions` / 重算 `ctr` | `impressions ≥ FLOOR` 且 `ctr < 同位次经验区间下界` | 标题/描述重写 → **站点接入**（`site_patch` 的 `title_meta` 类） |
| 2 | `demand_without_content` | 汇总 query × 关键词库 × 站点页面清单 | query 有曝光，但**关键词库里没有这个词**、且站内**没有对应主题页** | 补内容 → **文章管理**（`article_direction_add`）+ 回写**关键词库** |
| 3 | `ai_citation_gap` | `ai_answer` 面 × `web_search` 面 | 传统面该 query **有点击**，AI 面**引用量为 0 或缺失** | GEO 缺口 → **行动中心**（`source_layout`） |
| 4 | `landing_role_mismatch` | 汇总 `page_url` × `geo-crawler` 页面角色 | 流量集中在 `role: other` 的页面，而 `home` / `product` 无量 | 信息架构 → **行动中心**（`site_structure`） |
| 5 | `crawl_blocked_with_demand` | 汇总指标 × `SitePage.crawlable` × `robots.txt` | **有曝光的页面**在站点接入里 `crawlable = false` 或 robots 挡了 AI 爬虫 | 直接生成 `robots_txt` 补丁 → **站点接入** |
| 6 | `trend_divergence` | `SearchTrendPoint` × `DiagnosisOverview` 历轮 | 品牌词搜索量升而品牌覆盖率降（或反向），差值超过区间 | 进 **M5 告警**（`AlertItem`，复用既有 4 类型） |

- 🔴 **规则 3 与规则 5 是本轮的产品差异化**：规则 3 把"传统搜索有真实需求、但 AI 答案里没有我们"
  量化成一条可执行的缺口（这正是 GEO 的定义）；规则 5 是**站外数据与自有探测唯一的硬咬合点**
  ——"这个词一个月 800 次曝光，而落地页被 robots 挡着 AI 爬虫"是**任何单一数据源都得不出的结论**。
- 🔴 **归一让规则 1 变强也变险**：变强是因为跨平台求和后 `impressions` 的量级更真实（不再只看一个引擎）；
  变险是因为**"同位次经验区间"是按引擎分的**（Google 第 3 位与百度第 3 位的 CTR 基准差很多）
  ⇒ 判据必须**按 `region` / 引擎分组取基准**，不能拿一个全局曲线去套汇总值（§10 待确认 3）。
- 🔴 **规则 2 有意保守**：判据里"站内没有对应主题页"要用 `geo-crawler` 的真实页面清单，
  demo 里那份是静态的（`SEED_SITE_PAGES`）⇒ demo 端出的规则 2 机会**不代表真判定**，
  这条要被 `webmasterData.staticNote` 覆盖到。
- 每条机会带 `confidence`，沿用 M4 的 `REVIEW_CONFIDENCE_FLOOR = 0.75`（`api/constants.ts:40`）
  做"进不进复核队列"的同一道门槛 ⇒ **不新造第二套置信度口径**。

### DR-105 · 合规、溯源与陈旧告警

- **溯源四件套常驻**：每个数字都能追到 `source_kind` + `surface` + 区间（`period_start..period_end`）

- 🔴 **数据陈旧告警**：`data_through` 早于 `STALE_AFTER_DAYS`（常量，建议 **35** 天，

### DR-107 · 声明式指标映射表（版本化 + 可审计）🆕

  `{ source_kind, native_field, canonical_metric, tier: 'a'|'b'|'c', unit?, note_i18n_key, since_version }`。
- 🔴 **为什么必须版本化**：百度《AI 流量分析》**至今没有公开字段文档**（维度全来自站长实测截图与官方站内通知），
  灰度期随时可能改；搜狗 / 头条的列名也没有稳定的公开契约。⇒ 每行带 `since_version`，
  每条 `SearchQueryMetric` 记下自己进来时的 `mapping_version`，
  这样任何数字都能回答"**当时是按哪个口径映射进来的**"。
- 🔴 **未映射字段不得静默丢弃**：进 `native_extras` 原样留档，并在 C 类面板里渲染（产品负责人裁定 3 的
  "无法映射的维度单独展示但标注平台"）。**静默丢弃是最坏的失败形态**——平台加了一个新指标，
  我们悄悄扔了，客户在自己后台看得到、在我们这儿看不到，信任当场崩。
- 映射表是**数据不是算法** ⇒ demo 可以持有真表并真查（DR-99），
  真后端落地时**同一份表要搬到 `geo-domain`**（登记进 E-67 的 Plan C 义务），两端不得各写一份。

### DR-108 · 源目录表：加一个源只加数据、不改页面 🆕
- `SEARCH_SOURCE_CATALOG`（落 `api/search-catalog.ts`）：每个 `kind` 一行，字段含
  `{ kind, label_i18n_key, group, region, phase, auth_modes[], binding_fields[], alias_columns{},
    data_through_rule, docs_url, metric_notes_i18n_key }`。
- 🔴 **这条是产品负责人"后期还要接搜狗 / 360"的直接架构后果**：源会持续增加，
  就**不能每加一个源改一次页面**。加一个源 = 目录表加一行 + 映射表加几行 + 词典加几个键，
  **页面代码零改动**；编译期完整性网（`ValuesAreComplete<SearchSourceKind, typeof SEARCH_SOURCE_VALUES>`）
  负责在漏配词典或漏配目录时**编译不过**。
- `data_through_rule` 收各源的更新节奏（GSC 延迟 2–3 天、搜狗每日 15:00 后可查前一日、
  头条每日更新且新站有延时、百度统计近实时、百度 AI 流量分析灰度期可能空白）⇒ DR-109 用它算交集区间。
- `alias_columns` 收各平台导出列名到我们三张模板列的对照（DR-98），界面上据此渲染"怎么导"的说明。
  🔴 **`baidu_ziyuan_ai` 的别名现在有一级出处**（2026-10-12 官方导出文件表头原文，§3.2 实测 ③）：
  `关键词→query`、`AI引用量→citations`、`AI曝光量→impressions`、`AI点击量→clicks`、
  `AI点击率→ctr（仅交叉校验）`；其余平台仍按各自导出 / 后台表头补别名，
  🔴 **每补一条都要在判据里写明出处**（导出文件或截图，录进 `fixtures/search/`）。

### DR-109 · 时间对齐：汇总区间自动收敛到各源交集 🆕（产品负责人裁定 5）
- 每个源存 `data_through`（数据截至日），由 `data_through_rule` + 导入内容的 `period_end` 共同决定
  （**取更早的那个**：导出的周期到 9/30，但平台只更新到 9/28，就以 9/28 为准）。
- 🔴 汇总"近 30 天"时，若某个已接入的源只到 9/27，直接相加会**静默少算**那个源最后三天
  ⇒ **合计区间自动收敛到各参与源的交集**，并把收敛后的区间**打在合计旁边**：
  "汇总区间 09-01 ~ 09-27（受 GSC 数据延迟限制）"。
- `aggregate_window` 由 `search_board` 一并返回（DR-94），前端不重算——**避免两端各算一份区间**。
- 🔴 用户显式选了超出交集的区间时：**不静默截断**，而是给一个可选开关
  "按各源自己的可用区间相加（数字会偏低）"，默认**关**，开启时合计行挂红色旗标。
  静默截断会让用户以为看到的是完整 30 天。
- 单源视图**不受**交集收敛影响（看一个源就该看它自己的完整区间）。

### DR-110 · 完整性标记：`completeness` 三值 + 参与合计但挂旗 🆕（产品负责人裁定 5）
- `SearchQueryMetric.completeness` = `full` | `sampled` | `partial`：
  - `sampled`：GSC 超过 **5 万行/天/资源/searchType** 时的**静默采样**（平台不报错，只是少给行）；
  - `partial`：平台自陈数据不全（百度《AI 流量分析》灰度期"站点验证初期看到数据空白属于正常现象"、
    头条"新注册站点数据提取存在延时"、搜狗"不支持目录级别查询"）。
- 🔴 **非 `full` 的源参与合计，但合计行必须挂旗标**（产品负责人裁定）：
  剔除会让合计**忽大忽小**（客户接了第三个源，总数反而变小），比挂旗标更难解释。
  旗标文案给到"哪个源、为什么、影响方向"：例如"含 GSC 采样数据（超出每日 5 万行上限），合计可能偏低"。
- 🔴 **护栏：`analytics` 组永不参与 A 类合计**。百度统计的会话数 / 访问数是**站内量纲**，
  不是 SERP 量纲；混进曝光合计，"总曝光"当场变成假数。这条要有**专门的判据**（§7 变异 ②）。
- 🔴 **护栏：B 类永不跨平台平均**。合计 CTR 只能 = Σclicks ÷ Σimpressions（同 surface、同区间、同参与源）。

### DR-111 · 接入建议：按客户自己的流量来源推荐该接哪几个平台 🆕（产品负责人裁定 5）
- 缘起：产品负责人指出"数据源的多少取决于站点访客用哪个引擎"⇒ 那么**我们不该猜，该问数据**。
- 形态：`analytics` 组（百度统计 / 未来的 GA4）接入后，用它的**来源分析**算出搜索引擎分布，
  在「站长平台」组顶部给一条建议：
  "你的站内流量 62% 来自百度、18% 来自头条、11% 来自 Google ⇒ 建议优先接这 3 个站长平台；
  搜狗 / 360（二期支持）合计 <3%，可以等。"
- 🔴 **不硬编码任何默认推荐**：市场份额数据各来源差异极大（§3.4b：同一时期百度份额有 38.1% 与 53.32%
  两种口径），任何内置假设都会在某个客户身上错得离谱。**没有 `analytics` 数据时不显示建议**，
  而不是显示一份通用推荐。
- 🔴 这条建议**不是** DR-100 的 7 号规则：它不产出"优化机会"，只产出"该接哪个源"，
  且不进 `SearchOpportunity`（避免把产品引导混进客户的优化清单）。
- demo 侧：建议的**展示与文案**真做（DR-99 ⑥），但**分布数字来自种子**（`SEED_SEARCH_TRAFFIC_SPLIT`），
  因为 demo 没有真的百度统计连接。

### DR-112 · 汇总视图的筛选面 🆕（产品负责人裁定 3 的后半句）
- 四个筛选维度，**全部在前端 compose 层做**（DR-97 ④：不加 `search_aggregate` 命令）：
  ① **时间**（预设 7/28/90 天 + 自定义；受 DR-109 交集约束）；
  ② **平台**（多选；默认全选已 `ready` 的源；🔴 取消勾选任一源，合计与 B 类**当场重算**，
  并且 `aggregate_window` 也跟着重算——因为交集变了）；
  ③ **面 `surface`**（`web_search` / `ai_answer` / 两者；默认 `web_search`，跨面合计要显式选且带标注，DR-95）；
  ④ **维度**（按关键词 / 按页面 / 按平台三种透视）。
- 🔴 筛选态只存 `useState`（刷新即重置，与 DR-76 视图切换同一口径），**不**落 localStorage。
- 🔴 合计行**永远显示参与源清单**（可展开），不只显示一个数字——这是 DR-95 撤回"没有总曝光"时
  一并认下的义务：**给数字，同时给得出这个数字的账**。



### DR-113 · 粘贴解析作为**一等**接入形态（2026-10-12 新增，采纳路径 D）🆕
- 🔴 **建模修正**：原 DR-93 的 `SearchAuthMode` 把"凭据形态"与"取数方式"混成了一个字段。
  拆成两个正交维度：
  - `auth_mode`: `none` | `oauth`（**只描述凭据**）；
  - `ingest_modes[]`: `api` | `file_import` | `paste_parse` | `manual_entry`（**描述数据怎么进来**，可多选）。
  这样"百度《AI 流量分析》= `auth_mode: none` + `ingest_modes: ['paste_parse','manual_entry']`"
  与"GSC = `auth_mode: oauth` + `ingest_modes: ['api','file_import','paste_parse']`"都能一句话表达，
  二期加源也不用再动模型。
- `paste_parse` 的解析器落 `api/search-paste.ts`（前端纯函数，可单测）：
  ① 嗅探分隔形态（TSV / HTML `<table>` / 逗号）；② 用 `alias_columns`（DR-108）按**表头文字**认列，
  **不要求列序**；③ 认不出的列进 `native_extras`（DR-107，**不静默丢弃**）；
  ④ 数字里的千分位逗号、百分号、中文"万"要归一（`1.2万` → `12000`）；
  ⑤ 行级错误**指到粘贴内容的第几行**（复用 `prompt-csv.ts` 的错误行号口径，DR-98）。
- 🔴 **粘贴解析不是 CSV 导入的替代，是它的前置**：两者共用同一套列识别与校验，
  差别只在"文本从哪来"⇒ 实现上 `search_metric_import_csv` 这一条命令**同时吃文件与粘贴文本**
  （入参 `payload` 已经是字符串，`prompt_set_import_csv` 就是这么做的）⇒ **命令面仍是 6 条，不加命令**。
- 合规（§3.4c 路径 D）：取数动作发生在**客户自己的浏览器**里，我们不持有凭据、不向平台发请求、
  不绕过技术措施 ⇒ 界面上要有一句常驻说明 `webmasterData.pasteNote`：
  "复制粘贴在你自己的浏览器里完成，本软件不保存你的平台账号密码，也不会代你登录任何平台。"
  🔴 这句话**是产品承诺，不是免责套话**——它与 DR-114 的"不做"互为表里，写上去就得守住。

### DR-114 · 不做模拟登录；"本机只读屏"列三期并带三个前置条件 🆕
- 🔴 **本轮与二期都不做**"用户预配账号密码 + 模拟登录抓后台"（§3.4c 路径 B）。
  四条理由逐条有出处：百度用户协议**禁止出借账号密码**且**账号所有权归百度**（B-1）；
  **三重授权原则**缺第二重"平台授权"（B-2，新浪微博诉脉脉案，北知院终审，判赔 200 万 + 20.9 万）；
  **反法（2025 修订）第十三条第三款"数据专款"** + 北京互联网法院 2026-06 首例判决（判赔 23 万余元，
  点名的正是"登录验证措施、访问权限管理措施、可追踪加密参数"）（B-3）；
  **风控会打到客户账号上**、且百度账号是全身份凭据（B-4，与 AGENTS 规则 3 精神冲突）。
- 🔴 **这条要写进产品定义级的约束，不只是本模块的取舍**：任何"我们替客户登录第三方平台"的需求
  （不限于百度，包括头条 / 搜狗 / 360 / GSC / Bing）**一律走官方 OAuth**，
  没有官方 OAuth 的就走 `paste_parse` / `file_import` / `manual_entry`。
  ⇒ 建议把这句抄进 `AGENTS.md` 硬性规则（本轮已在 AGENTS.md 的 M5.5 条目里点了）。
- **三期选项：本机只读屏**（§3.4c 路径 C）——桌面端读取**用户自己已登录的浏览器会话**中
  已经渲染出来的数据，不碰凭据。三个前置条件**全部满足**才开口：
  1. **改产品定义 §3.12**（`:336` 现在明确 ❌ 浏览器插件）——这是产品负责人的权限；
  2. **法务审读各平台协议**中关于自动化访问 / 浏览器扩展的条款（百度搜索资源平台、头条、搜狗、360 各一份）；
  3. **架构约束写死**：只读、不写、不代提交、不碰凭据、不绕过任何验证或风控，
     且 🔴 参考 **Amazon v. Perplexity**（9th Cir. 2026-08-04, No. 26-1444）那条裁定的**局限**——
     它很窄、不终局、**不赋予普遍抓取权**、且**不排除合同 / 隐私 / 反不正当竞争责任**
     ⇒ 不能把它当成"绿灯"，只能当成"这个架构在'谁是访问主体'这一问上有辩护空间"。
- **2026-10-12 追加：用户在场 RPA 的二期开口条件**（回应产品负责人第三轮"要全自动化"）。
  "用户本机 + 用户已登录会话 + 用户在场触发 + 不绕任何验证 / 风控"的只读 RPA，与路径 B 的
  "我们持有凭据、服务端代登录"**风险等级不同**（无凭据托管、无异地风控、请求出自用户本机），
  但**仍不干净**：平台协议对自动化读取的禁止、三重授权缺"平台授权"这两条**没有消失**，
  账号被限的后果仍落在客户头上。⇒ 维持"默认不做"，但把开口写成**四条可判定的门禁**，
  全部满足才进二期排期，否则留在三期：
  ① 法务对百度 / 头条 / 搜狗 / 360 四份平台协议出具**书面意见**，认为该形态可接受；
  ② 产品定义 §3.12 修订（现 ❌ 浏览器插件；RPA 驱动用户自有浏览器是否落入该条，由产品负责人裁定）；
  ③ 至少一个付费客户**书面接受**"账号可能被平台限制"的风险条款；
  ④ 该源**仍无官方 API** 且其数据被销售侧证明**影响成单**（有单可丢才值得冒账号风险）。
- 🔴 **先行者佐证**：Semrush / Ahrefs 的自动化靠自建索引 + 官方 OAuth，**不做模拟登录**（§3.6）；
  "参考 semrush"在它们自己的实践里**推不出**模拟登录这条路。
- 🔴 **代价认下来**：不做路径 B/C 意味着 `baidu_ziyuan_ai`（本轮最有价值的源）
  **永远需要客户动一次手**（复制或导出，月度约 5 分钟）。这是**用一点摩擦换掉法律与账号风险**，
  划算；但要如实告诉一线销售，别承诺"全自动"。

### DR-115 · CTR 经验基准：站点自身分位数优先，外部曲线只作冷启动兜底且必须标出处 🆕
（本节同时落地产品负责人"需要标出处"的指示。）
- 🔴 **不用外部曲线做主基准**。理由是三份主流研究的**第一位 CTR 差近一倍**，且**全是 Google / 英文 SERP**：
  - **SISTRIX**（分析 Google 逾 8,000 万关键词、数十亿搜索结果）：#1 **28.5%**、#2 15%、#3 11%、#10 2.5%；
    第二页各位置均 <1%；排名上升一位平均相对 CTR +30.8%（#6→#5 最高，+53.2%）
    （出处：`www.bilibili.com/read/mobile?id=25784667`、`m.sohu.com/a/712265413_121769793`）；
  - **Backlinko**：#1 **31.73%**、#2 24.71%、#3 18.66%、#4 13.60%、#5 9.51%
    （出处：`baijiahao.baidu.com/s?id=1758469161657954342` 一类转载；原始研究见 Backlinko Google CTR Study）；
  - **Semrush（2023，移动端）**：#1 **22.4%**、#2 13%、#3 10%
    （出处：`www.semrush.com/blog/google-search-statistics/`）；
  - **Advanced Web Ranking（分行业 / 分设备 / 分查询类型）**：2025Q1 桌面 #1 在**教育行业 45.35%**、
    **宠物行业 15.75%**；品牌词、信息词、商业词的 CTR 季度变化各有 1–3.5 个百分点的漂移
    （出处：`k.sina.cn/article_1084407072_40a2bd2000101crqg.html`、`k.sina.cn/article_1084407072_40a2bd20001ak6e.html`）。
  ⇒ 22.4% / 28.5% / 31.73% / 45.35% 都能自称"第一位的平均点击率"。
  🔴 **拿这种曲线当阈值去判"这个页面的标题不行"，客户一查就穿**；
  而且**百度 / 头条 / 搜狗根本没有可比口径的公开曲线**（DR-100 已指出基准必须按引擎分组）。
- **裁定：主基准用"站点自身分位数"**——把该站点在同一 `surface`、同一引擎、同一区间内
  所有 query 的重算 CTR 取分布，用**同位次分档的自身中位数**作为基准；
  规则 1 的判据改成"**该 query 的 CTR 低于同位次档自身中位数的 X%**"（X 为常量）。
  优点：① 对所有引擎一致、不需要外部数据；② **不会被质疑口径**（这是你自己的数）；
  ③ 天然满足 DR-100 "基准必须按引擎分组"（分位数就是按引擎各算各的）。
  🔴 代价：需要**足够样本**（建议 `MIN_QUERY_SAMPLE = 30`，与 `api/constants.ts` 里
  `MINIMUM_SAMPLE_SIZE = 30` 同口径，**不新造第二个样本量常量**）；样本不足时**规则 1 不出机会**
  （宁缺勿滥，与 M5 对 `sample_size_grade: 'insufficient'` 置灰的既有姿态一致）。
- **外部曲线只作冷启动兜底**，且必须满足三条：
  ① **界面标出处**（机构名 + 研究年份 + 链接），文案走词典 `webmasterData.ctrBenchmark.source`；
  ② 标"**英文 SERP 经验值，仅供冷启动参考**"（规则 6 精神：不作无法兑现的承诺）；
  ③ 只用作**参考带（区间）**、不用作阈值，且冷启动期**规则 1 的 `confidence` 强制压低**
  （低于 `REVIEW_CONFIDENCE_FLOOR` ⇒ 进复核队列，与 M4 同一道门槛）。
- 🔴 **`api/constants.ts` 里不写死任何一条外部曲线的数值**。理由：这些数字会过期
  （AWR 每季度都在变），写死就是造一份**没人负责更新的假真值源**。
  改为：外部曲线以**带出处与生效日期的数据文件**形式存在（`api/search-benchmark.ts`，
  每条带 `source` / `url` / `as_of` / `surface` / `engine`），并且**默认不参与判定**，
  只有用户在设置里显式开启"冷启动参考带"才生效。

### 5.2 种子自洽纪律（照 `seed/diagnosis.ts` "手工满足公式" 的既有姿态）
🔴 demo 不算 6 条规则，但**映射、求和、重算、区间收敛是真算的**（DR-99），
所以种子必须手工算对，判据全部落 `demo/seed.test.ts`：
1. 每行 `SearchQueryMetric.ctr` == `clicks / impressions`（容 ±0.001）；
2. `SearchAiOverview.ai_ctr` == `ai_clicks / citations`——🔴 **分母是引用量，不是曝光量**
   （百度官方口径，§3.7 结论 4；这是全份种子里最容易写错的一个数，单独一条判据钉住）；
3. 每个周期的 `SearchTrendPoint`（单源）== 该周期该源导入行按 `surface` 求和；

   且**汇总 `ctr` == Σclicks ÷ Σimpressions**，判据要显式断言它**不等于**各源 ctr 的算术平均（DR-110 护栏）；

### 10.5 第三轮指示（2026-10-12）："要全自动化，参照 Semrush / Ahrefs"——客观评估与侦查结论
**指示要旨**：手动填报 / 导入后期基本不会使用；希望全部自动化，经 API 或模拟登录去各平台采集；
参照国外 Semrush / Ahrefs 的做法；要求客观评价 + 前瞻性侦查 + 按实际调整设计。
第四轮（同日）：**针对网站添加自建索引，参考 Semrush / Ahrefs 但只做关键性数据采样**；
**DR-117 挂成定时任务**；**开 demo 轮**。

**客观评估（先结论后证据）**：
1. **"全自动化"方向对，但对象要拆开**。能自动化的源（百度统计 / GSC / Bing WMT 传统面）**本来就在
   自动化路上**——三家 OAuth 全做（DR-93），令牌刷新后定时拉取，客户零动手。不能自动化的是
   **第一方控制台的 AI 引用数据**（百度《AI 流量分析》、GSC 生成式 AI 报告、Bing AI Performance）：
   §3.4c 路径 A 已核无 API；本轮侦查再确认 **GSC 的 Search Analytics API 至今没有生成式维度**
   （UI 报告仅曝光，点击要等英国 CMA 承诺落地）、**Bing WMT API 仍不含 AI Performance**。
2. **"参照 Semrush / Ahrefs"恰好推不出模拟登录**。侦查确认它们是**两条腿**：腿 1 自建索引
   （Ahrefs 官方自述 "crawl the entire web 24/7 and store petabytes"；AhrefsBot / SemrushBot 是
   Cloudflare Radar 上 SEO 类活跃度前二的爬虫；Semrush 2025 的 AI Visibility、Ahrefs 的 AEO 追踪
   都建在自家采样上）；腿 2 官方 OAuth（原生集成 GSC + GA4）。**两家都不登录客户站长后台**，
   百度控制台数据它们**也没有**。连卖 GEO 服务的公司 today 的做法都是"代客注册 Bing WMT + 报告截图"
   ⇒ 控制台第一方数据无自动通道是**行业现状**，不是我们的能力缺口。
3. **模拟登录维持不做**（DR-114 不变），但把"用户在场 RPA"从模糊的三期改成**四条可判定的开口条件**
   （法务书面意见 / 产品定义 §3.12 修订 / 客户书面接受账号风险 / 该源无 API 且影响成单）。
   四条风险不因"客户想要自动化"而消失：百度协议禁出借凭据、三重授权缺平台授权、
   反法 13 条 3 款、风控打到客户账号。

**按实际做出的设计调整（四条）**：
- **DR-90 二次重定位 + DR-116**：主喂料 = L1 自有抽样（M3 `geo-crawler`，我们的"AhrefsBot 腿"，全自动）
  + L2 官方 API；控制台导入 / 粘贴 / 填报**降为对账层**（L3），用平台第一方数字校准自有抽样偏差，
  冲突以 L3 为准并记差异事件；页面加"自动采集状态卡"让自动化看得见。
  ⇒ "导入基本不会用"的担心**成立且被采纳**：导入从来不该是主喂料，它是对账。
- **DR-117**：把"等平台开 API"从被动等待变成**带触发条件的观察清单**（五项，触发后动作 =
  目录表翻面、页面零改动），季度复查，可挂定时自动化代跑、无变化保持沉默。
- **§3.6 重写**：两腿模型的抄法——抄腿 1 之形（自有抽样只回答 AI 引用可见性、**不估算曝光**）、
  全抄腿 2、不抄模拟登录与点击流估算。
- **DR-114 追加**二期开口四条件 + 先行者佐证。

**未采纳的部分（理由留档）**：
- "模拟登录自动化采集"不采纳（法律与账号风险，见上；且先行者无人这么做）；
- "自建全网索引 / 点击流估算曝光"不采纳（没有数据资产，估算值无说服力，§3.6 原裁定维持）；
- "现在就把 RPA 排进二期"不采纳（四条件未满足前排期 = 给销售一个兑现不了的承诺，规则 6 精神）。
